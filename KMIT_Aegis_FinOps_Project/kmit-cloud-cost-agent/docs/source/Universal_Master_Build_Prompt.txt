1. CORE PRODUCT
================================================================

Build a real agentic autonomous cloud cost-optimization platform running against a simulated cloud environment.

The core loop must be:

Natural-language request
→ AI agent investigates through tools/APIs
→ gathers evidence
→ proposes action or no_action
→ deterministic safety engine allows/rejects
→ controlled action API executes
→ fresh state retrieved
→ verification engine checks actual outcome
→ final auditable response

The AI must genuinely decide:
- what to investigate
- which tools to call
- which service/evidence matters
- what action to propose
- when no action is appropriate

Do NOT build a rule engine with an LLM attached for decoration.

Do NOT hard-code the answers to the supplied scenarios.

The system must continue working if metrics, services, traffic, timestamps, costs, constraints, or outcomes change.

================================================================
2. NON-NEGOTIABLE SAFETY MODEL
================================================================

AI can reason and propose. It is NOT the final authority.

A centralized deterministic Safety / Policy Engine must independently validate every action before execution.

At minimum validate:
- service exists
- action is supported/eligible
- observation freshness
- minimum capacity
- maximum capacity
- latency requirement
- availability requirement
- health
- action parameters
- current-state consistency
- recent conflicting actions/events where applicable

AI must NEVER bypass a safety rejection.

Separate these states:
PROPOSED
AUTHORIZED
EXECUTING
EXECUTED
VERIFIED
FAILED
BLOCKED
PARTIAL
UNKNOWN

Never treat “requested” as “successful”.

4. STALE / CHANGING DATA
================================================================

Freshness is a first-class safety signal.

Implement:
- observation timestamp
- current time
- observation age
- configurable freshness threshold
- explicit fresh/stale status

If observations are stale or materially inconsistent:
1. block risky action
2. fetch fresh state
3. reassess
4. continue only when the new evidence passes safety validation

This behavior must be visible in the UI and audit trail.

5. SOURCE SCENARIOS
================================================================

Use the exact Test A, B, C, and D data from the attached original problem statement.

Do NOT invent alternative versions of these tests.

TEST A — COST OPTIMIZATION
The source includes orders-api and reports-worker. reports-worker has 0 RPM and 4 instances. Treat it as an investigation candidate, NOT as an automatic “stop” answer. The agent should inspect relevant evidence and decide.

TEST B — RISING TRAFFIC
The source has orders-api traffic increasing from 2,100 to 4,200 RPM, latency at 260 ms against a 300 ms limit, with moderate CPU/memory. Evaluate the combination of traffic trend, latency, utilization, capacity, and constraints. Do not hard-code “scale up”.

TEST C — STALE OBSERVATION
The source contains an older checkout-api state at 08:00 UTC and newer traffic at 10:30 UTC with a dramatic workload difference. The agent must detect stale/inconsistent state, block blind optimization, fetch fresh state, and reassess.

TEST D — FAILED ACTION
The source contains payment-api under load and an attempted scale-up to 5 instances that fails with:
capacity_unavailable
The system must preserve the failure, never claim success, retrieve fresh state, and report the verified outcome.

Automate all four scenarios and make them runnable from both tests and the UI.
